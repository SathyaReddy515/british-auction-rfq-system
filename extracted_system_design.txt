1. Purpose and Source of Requirements
This document is the final proposed system design and database schema to accompany the British Auction in RFQ System hiring assignment. The company assignment PDF is the source of truth for required business functionality. The Full Stack Intern JD guides technology selection.
Assignment requirements: RFQ creation, auction timing, forced close, X-minute trigger window, Y-minute extension, three extension trigger choices, quote fields, auction listing/details, activity history and four deliverables.
JD-aligned stack: Python/FastAPI, React and PostgreSQL. Celery with Redis is selected for background jobs; Neo4j is optional/good-to-have and is not required for the core relational workflow.
This document defines a proposed implementation design. It does not claim that code has already been built or tested.

3.3 Main data flow
Buyer creates an RFQ and supplies bid start, initial close, forced close and service date. The backend validates and stores the RFQ and auction configuration.
Suppliers submit quote details and participate in the auction when it is active.
A bid request reaches FastAPI. The backend authenticates the supplier, validates eligibility and checks the current auction state using server time.
The bidding service persists the bid in a transaction, calculates each supplier's current bid/rank and evaluates the selected extension trigger.
If a trigger qualifies, the effective close time is extended by Y minutes but capped at the forced close time. Bid and extension events are recorded in the activity log.
After commit, WebSocket updates are published to authorized connected clients. A close-check task is scheduled or reconciled.
At task execution, the Celery worker re-reads PostgreSQL. It closes the auction only if the latest effective close time has passed; stale or duplicate tasks must not close it early.
3.4 Critical consistency and security controls
PostgreSQL is the source of truth for auction status, current close time, bids and activity events.
Serialize bid processing per RFQ using a database transaction and row-level lock (or equivalent) so concurrent bids cannot corrupt rankings or extension decisions.
Use server-generated timestamps. Never trust a timestamp supplied by the browser.
Make close tasks idempotent. A delayed, duplicate or stale task must re-check the current close time and status before changing state.
Commit bid, extension and activity records atomically. Publish WebSocket messages only after commit.
Apply role-based access: buyers manage their RFQs; suppliers can participate only when eligible; supplier visibility must follow the chosen privacy policy.

4.1 Three extension trigger types
Trigger type
Condition to extend
BID_RECEIVED
A valid bid is accepted inside the trigger window.
ANY_SUPPLIER_RANK_CHANGE
At least one supplier's rank changes after a qualifying bid inside the trigger window.
L1_RANK_CHANGE
The identity of the lowest-priced supplier changes after a qualifying bid inside the trigger window.
A price reduction by the current L1 supplier does not itself satisfy L1_RANK_CHANGE if the identity of L1 remains unchanged.
4.2 Pricing assumption to confirm
The assignment lists freight, origin and destination charges on the quote form and separately describes suppliers lowering prices. This design treats bid_amount as the total competitive price for the RFQ; the quote stores the charge breakdown. If the intended behavior is that each rebid changes individual charge components, the bid model must be expanded to store a component-level breakdown or a versioned quote snapshot.
4.3 Winner selection assumption
The assignment requires bids sorted by price and supplier ranking, but does not explicitly state that the system automatically awards the RFQ. Therefore, the design stores a final result snapshot and allows the winner-selection policy to be confirmed. A buyer may select the winning supplier after closure; the lowest price should not automatically be treated as an awarded contract without that decision.

6. Core Transaction Flows
6.1 Bid submission and extension
Begin a database transaction and lock the relevant RFQ row.
Read current status, server time, effective close, forced close and auction configuration.
Reject if auction is not ACTIVE, has not started, or current time is at/after effective close.
Validate supplier participation and bid price against the supplier's previous accepted bid and the documented price policy.
Insert the bid with a server-generated timestamp and idempotency request ID.
Calculate supplier rankings before and after the bid using each supplier's latest valid bid.
Evaluate the configured trigger against the event time and trigger window [current close - X, current close).
If triggered, set current close to the earlier of current close + Y and forced close; record the extension reason and old/new close times.
Insert bid and extension activity events, then commit.
After commit, publish WebSocket events and schedule/reconcile the closure task.
6.2 Scheduled closure
Celery Beat or a scheduled task dispatches a close-check job for the auction.
The worker loads the RFQ from PostgreSQL and checks its latest status and current_bid_close_at.
If the auction is not active, the task exits idempotently.
If current time is earlier than the latest close, the task does not close the auction and schedules/reconciles another check.
If the forced close time has been reached, set FORCE_CLOSED; otherwise, if the effective close has been reached, set CLOSED.
Record the closure event and result snapshot in a transaction, then publish a WebSocket status update after commit.

8. Assumptions Requiring Confirmation
Open point
Proposed decision
Do multiple extension triggers apply simultaneously?
One selected trigger per auction initially; confirm whether multi-select is required.
Does bid amount mean total quote price or individual charge components?
Treat bid_amount as total competitive price; retain charge breakdown on quote.
Which bid represents a supplier's current ranking?
Latest valid bid per supplier.
How are equal prices ranked?
Earliest accepted timestamp at that price, then deterministic tie-break.
Is the lowest bidder automatically awarded the RFQ?
No automatic award assumed; buyer selection is recorded separately.
What can suppliers see about competitors?
Restrict sensitive quote details; expose only fields required by the agreed auction transparency policy.
